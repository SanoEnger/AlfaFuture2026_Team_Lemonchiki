# Умный кредитный кабинет предпринимателя

Автономный демонстрационный кредитный процесс: заявка → локальные проверки → объяснимый скоринг → решение сотрудника → ответ клиента. Все компании, новости, документы и кредитные операции синтетические. Реальные деньги не выдаются.

Backend — Вахрушев; PostgreSQL, ORM, миграции и сиды — Смирнов; скоринг, моки, сборка и интеграционные проверки — Волосников.

## Запуск

Требуются Docker Desktop с Linux containers и Python 3.12 или 3.13 для первоначальной генерации локальных настроек. Команды выполняются из корня репозитория:

```powershell
python scripts/setup_env.py
docker compose up --build -d --wait
```

На Windows вместо `python` можно использовать `py -3.13`. Скрипт создаёт `.env` со случайными паролем PostgreSQL и ключом JWT; существующий файл сохраняется. Значения не выводятся и исключены из Git. В ручном `.env` используйте пароль БД из hex-символов либо URL-кодируйте специальные символы, поскольку он включается в DATABASE_URL. Если порт занят, поменяйте `API_PORT`.

Доступны [Swagger](http://127.0.0.1:8000/docs), [OpenAPI](http://127.0.0.1:8000/openapi.json) и [health](http://127.0.0.1:8000/health). PostgreSQL не публикует порт на хост. Миграции выполняются отдельным сервисом до сидов; API стартует после их успешного завершения. Контейнер API работает без root; БД и PDF находятся в отдельных постоянных volumes.

| Логин | Пароль демо-приложения | Роль |
|---|---|---|
| client_good | Demo2026! | Предприниматель, здоровый бизнес |
| client_risky | Demo2026! | Предприниматель, рискованный бизнес |
| banker | Demo2026! | Сотрудник банка |

Сиды создают три исторические заявки с LOW/100, MEDIUM/66 и HIGH/20; исходные финансы компании не перезаписываются. Повторное сидирование не обновляет старые риск-оценки: сохранённая `rules_version` описывает правила, по которым они были рассчитаны. Новая заявка получает текущую версию.

## Проверка

```powershell
# Все unit/API/PostgreSQL-тесты, включая миграции и два конкурентных решения.
docker compose run --rm tests

# Сквозные HTTP-сценарии через запущенный API.
docker compose run --rm smoke
```

Для полной проверки с перезапуском контейнеров:

```powershell
python scripts/verify_stack.py
```

Скрипт собирает и запускает стек, выполняет тесты и HTTP-сценарии, запоминает UUID, перезапускает PostgreSQL/API и повторно проверяет статусы, историю и содержимое PDF. Он создаёт только синтетические заявки и файл `.local/smoke-state.json`, не удаляет имеющиеся данные. Локальные тесты без PostgreSQL описаны в [backend/README.md](backend/README.md).

Ручной сценарий в Swagger: войти через `/api/v1/auth/demo-login`, вставить токен в Authorize; выбрать продукт, создать черновик и выполнить `/submit`. Под `banker` открыть карточку, посмотреть проверки и факторы, предложить условия. Под клиентом выполнить `/accept` и проверить `COMPLETED` и историю. Дополнительно: запросить уточнение, приложить PDF и выполнить `/resubmit`; под рискованным клиентом показать HIGH и решение об отказе.

## Состояние интеграции

React-интерфейс находится в `frontend`. Локальный запуск: `cd frontend`, `npm.cmd install`, `npm.cmd run dev`. Автономные сценарии доступны в `/demo-login`, локальная тестовая регистрация — в `/register`, интеграция с существующим FastAPI — через `/server-login`. Последний режим использует Bearer API и загружает серверные заявки, историю, документы и предложения. Подробности и ограничения: [frontend/README.md](frontend/README.md).

В Compose добавлен frontend с Nginx и прокси `/api`; адрес по умолчанию http://127.0.0.1:5173 (настраивается `FRONTEND_PORT`). Новая конфигурация контейнера подготовлена, но её Docker-сборка требует работающего Docker Engine. Полная серверная регистрация, cookie-сессии, приглашения и администрирование из master-ТЗ ещё не интегрированы; соответствующие frontend-сценарии работают отдельно на синтетических локальных данных.

Остановка: `docker compose down` сохраняет volumes. Команда с `-v` удалит БД и PDF и для обычного перезапуска не нужна. Состояние сервисов: `docker compose ps`; логи: `docker compose logs api migrate seed`.

Перед сдачей: пройти AT-01…AT-12 с UI, указать точный commit/tag, проверить доступ организаторов и подтвердить час дедлайна. Релизный тег создаётся после приёмки.

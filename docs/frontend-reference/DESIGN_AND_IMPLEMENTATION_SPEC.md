# SMART CREDIT — Graphite Professional
## Техническое задание на интерфейс и реализацию для Codex

Версия дизайна: 1.0
Формат проекта: локально запускаемое веб-приложение
Исходная постановка: «Умный кредитный кабинет предпринимателя», Альфа-хакатон 2026, редакция 1.1.
Дизайн: строгий, компактный, профессиональный Graphite Dark по умолчанию, полноценная Light-версия.

## 1. Цель

Реализовать рабочую банковскую веб-систему для предпринимателя и сотрудника банка. Интерфейс должен выглядеть как настоящий финансовый B2B-продукт, не как AI-generated шаблон.

Не создавать лендинг. Нужны маршруты, формы, статусы, проверки, реальные переходы между экранами и связанный кредитный workflow.

Сначала изучить существующий репозиторий и исходное ТЗ. Сохранить уже работающую бизнес-логику. SVG-файлы в архиве использовать как визуальные референсы.

## 2. Стек

- React + TypeScript + Vite.
- Mantine для доступных UI-примитивов, формы, модальных окон, theme provider.
- React Router для маршрутов.
- TanStack Query для API-запросов и серверного состояния.
- lucide-react для всех интерфейсных иконок.
- FastAPI, Pydantic, SQLAlchemy и Alembic.
- PostgreSQL.
- Docker Compose для локального запуска.
- Детерминированные моки реестра и БКИ.
- Локальный объяснимый балльный скоринг.
- Автономная работа без обязательных платных внешних API.

Не заменять имеющийся backend фальшивыми изменениями только в React state. Для временной работы без сервера использовать typed mock adapter, который можно заменить реальным API.

## 5. Клиентский кабинет

### Главная
Активная заявка, запрошенная сумма и срок, понятный статус, блок «Что дальше», прогресс, две программы, полезные новости. Если заявок нет — empty state и «Создать заявку».

### Список заявок
Компактная таблица, поиск, фильтры продукта и статуса, сортировка, дата изменения, ссылка на заявку. На мобильной ширине строки превращаются в карточки.

### Продукты
Два синтетических продукта: «Оборотный» и «Инвестиционный». Показывать назначение и условия из API. Не придумывать реальные банковские тарифы.

### Мастер заявки
1. Выбор продукта.
2. Сумма, срок, цель, комментарий.
3. Компания и финансы.
4. Проверка и отправка.

Автосохранение черновика, валидация, sidebar summary на desktop. Изменения после отправки допускаются только через формальный сценарий уточнения.

### Карточка заявки
Название, номер, статус, параметры, следующее действие, история, документы, банковские запросы, предложение или причина отказа.

### Уточнения
Банк запрашивает документы → NEEDS_INFO → клиент прикладывает PDF → resubmit → повторная проверка.

### Оффер
Отдельно показывать «Запрошено» и «Предложено» по сумме, сроку, ставке. Кнопки принятия и отказа с подтверждением. Сохранять исходные параметры заявки.

### Компания
Реквизиты, отрасль, возраст бизнеса, выручка, расходы, долговые платежи; проверка введённых данных. Фиксировать financial snapshot при отправке.

### Документы
Список файлов, привязка к заявке, статусы, PDF-upload с лимитом 5 МБ, сообщения банка. Проверять MIME-тип и содержимое файла на сервере.

### Новости
Локальная синтетическая лента, учитывающая отрасль и цель кредита. У материалов должна быть открываемая полная карточка. Маркировка демо-контента.

### Настройки
Светлая / Тёмная / Системная. Опционально плотность, контраст, reduce motion. Тема сохраняется между перезагрузками.

## 6. AI-помощник

AI-помощник — дополнительная функция по отношению к исходному MVP.

Плавающая кнопка или вход через topbar. Правая выдвижная панель, не перекрывающая главное действие на desktop; на mobile — полноэкранный диалог.

Контекстные сценарии:
- «Какой кредит выбрать?»
- «Как выбрать сумму и срок?»
- «Какие документы нужны?»
- «Что означает статус?»
- «Чем предложение банка отличается от запроса?»

Начальная версия может быть rule-based + FAQ с маркировкой демо-помощника. При использовании LLM — только модель с открытыми весами и локальная работа. Помощник не ставит финальный банковский скоринг, не одобряет и не отклоняет заявку, не меняет банковские данные без явного действия пользователя.

## 7. Кабинет банка

### Очередь
Фильтры, поиск, сортировка, компания, продукт, сумма, статус, LOW/MEDIUM/HIGH.

### Карточка
Вкладки «Данные», «Проверки и риск», «Документы», «История».
Балльная оценка 0–100, факторы с положительным/отрицательным вкладом, версии правил и результаты реестра/БКИ.

### Действия
- Запросить дополнительные сведения.
- Предложить скорректированные условия.
- Отказать.

Каждое действие логируется. Требуются подтверждения и причины решений. Банковский оффер хранится отдельно от requested terms.

## 8. Состояния бизнес-процесса

DRAFT, SUBMITTED, VERIFYING, NEEDS_INFO, UNDER_REVIEW, OFFERED, REJECTED, ACCEPTED, DECLINED, COMPLETED.

Основные переходы:
- DRAFT → SUBMITTED
- SUBMITTED → VERIFYING
- VERIFYING → UNDER_REVIEW / NEEDS_INFO
- NEEDS_INFO → SUBMITTED
- UNDER_REVIEW → NEEDS_INFO / OFFERED / REJECTED
- OFFERED → ACCEPTED / DECLINED
- ACCEPTED → COMPLETED

REJECTED, DECLINED и COMPLETED — терминальные статусы.

Правила переходов строго проверяются backend. UI не является источником истины.

## 10. UX и адаптивность

На каждом экране предусмотреть loading, empty, error, success, disabled, hover, focus-visible. Статусы должны различаться цветом И текстом.

Отображения: desktop 1440, laptop 1280, tablet 768, mobile 390 px.
Фокус клавиатуры, корректные labels полей, доступные контрасты, подтверждение необратимых действий.
Не использовать текст меньше 12 px для обычного контента.

## 12. Приоритеты реализации

P0:
- роли, авторизация demo-login;
- продукты, профиль;
- мастер и workflow заявки;
- банковская очередь и решения;
- проверки, скоринг, факторы;
- документы, уточнения, история;
- оффер и принятие/отказ;
- синтетические новости;
- локальный Docker запуск.

P1:
- полировка интерфейса и состояния;
- полноценный dark/light/system;
- адаптивность.

P2:
- AI-помощник, дополнительные настройки, история диалогов.

Если времени мало, не жертвовать P0 ради AI-функций.

## 13. Acceptance criteria

1. Весь процесс заявки работает сквозным образом.
2. Client и Bank имеют разные права.
3. API и UI согласованы по состояниям.
4. Скоринг объясняется причинами, а не только уровнем.
5. Запрос сведений и отказ работают и записываются в историю.
6. Оффер сравнивается с исходным запросом.
7. Темы переключаются без изменения структуры или контрастности.
8. Все контролы работают или явно disabled с объяснением.
9. Docker Compose запускает приложение и БД с нуля.
10. Проведены typecheck, build, unit/integration/E2E.
11. Скриншоты всех основных экранов совпадают по сетке, отступам, типографике и плотности с приложенными SVG.

## 14. Инструкция Codex

Сначала проанализируй исходное ТЗ и репозиторий. Не разрушай существующую архитектуру. Реализуй функциональный P0, затем дизайн-систему Graphite Professional и интерфейсы по screen reference files.

SVG-файлы — визуальные ориентиры, а не картинки, которые нужно вставлять на страницы. Реализуй их настоящими компонентами React/Mantine.

Не добавляй glassmorphism, 3D, декоративные градиенты, случайные hero-иллюстрации и одинаковые большие карточки вокруг каждой цифры.

Результат должен быть работающим локальным веб-приложением, а не статическим HTML-макетом.

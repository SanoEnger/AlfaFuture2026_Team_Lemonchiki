# 0. ГЛАВНЫЕ ИНСТРУКЦИИ ДЛЯ CODEX

Этот документ описывает **какие функции требуется реализовать, как они должны работать и как их проверить**. Конкретные Python-, TypeScript-, SQL- и CSS-реализации выбирает и пишет Codex на основе фактической архитектуры проекта.

## 0.1. Принципы работы

1. Сначала изучить существующий репозиторий, API, модели, миграции, бизнес-логику и пользовательские страницы.
2. **База данных уже спроектирована. Не создавать новую БД поверх существующей и не переписывать её по этому документу автоматически.**
3. Схема БД, предложенная ниже, — **кандидат для сравнения**, а не обязательная замена.
4. Если существующая структура удовлетворяет требованиям — использовать её без изменений.
5. Если есть пробелы — предложить минимальные расширения, объяснить необходимость, последствия и миграцию.
6. Не выполнять `DROP TABLE`, потерю колонок, удаление данных, массовую смену идентификаторов или разрушительные миграции без отдельного обоснования.
7. Сохранять рабочие маршруты, контракты и логику, если они соответствуют цели. Не дублировать API и компоненты.
8. Не реализовывать декоративные кнопки без действия.
9. Все проверки прав и разрешённых переходов выполнять на backend. Frontend только отражает доступные действия.
10. Все рабочие экраны получают данные из API. Источник истины — PostgreSQL. Автономный режим не предусмотрен.
11. Не заявлять, что функциональность реализована, пока не проведены тесты и не проверен пользовательский сценарий.
12. Не требовать от заказчика писать код: Codex самостоятельно выбирает библиотеки, типы, модели и реализацию.
13. Не изменять логику статусов заявки по собственному усмотрению.
14. Выполнять задачи последовательно по приоритетам P0, P1, P2.

## 0.2. Приоритет источников истины

При расхождениях действовать так:

- **Фактическая БД и рабочие API:** сначала изучить их устройство.
- **Согласованные бизнес-сценарии проекта:** сохранить смысл и допустимые действия.
- **Этот документ:** целевое функциональное поведение.
- **Ранее созданные CSS-файлы и визуальные макеты:** целевая визуальная система.
- **Новые предложения Codex:** только если они улучшают совместимость, надёжность или UX.

Не считать существующий баг правильным поведением только потому, что он уже присутствует в коде. Но и не менять структуру приложения без выяснения причин.

Если есть противоречие между существующей БД и требуемым сценарием, Codex обязан:
1. Описать обнаруженное расхождение.
2. Проверить, можно ли реализовать сценарий поверх текущей модели.
3. Сравнить несколько вариантов решения.
4. Выбрать наименее рискованный.
5. Зафиксировать результат и необходимые миграции.

# 1. КОНЦЕПЦИЯ И ГРАНИЦЫ ПРОДУКТА

## 1.1. Продукт

«ФинМаршрут» — локальное веб-приложение, позволяющее предпринимателю подавать заявки на кредит, отслеживать рассмотрение, обмениваться документами с банком и реагировать на предложения.

Сотрудник банка получает рабочее место для рассмотрения заявок, оценки риска, запроса данных и формирования решений.

Администратор банка управляет доступом сотрудников и распределением ответственности.

AI-помощник предоставляет контекстные справочные объяснения, но не принимает кредитные решения.

## 1.2. Пользовательские роли

Три базовые системные роли:

- `CLIENT` — предприниматель.
- `BANK_OFFICER` — сотрудник банка.
- `BANK_ADMIN` — администратор банковского доступа.

В интерфейсе два основных рабочих кабинета:
- клиентский;
- банковский.

`BANK_ADMIN` использует банковскую оболочку приложения с отдельным разделом администрирования.

## 1.3. Ключевые продукты MVP

Предусмотреть как минимум два кредитных продукта:

1. Оборотный кредит.
2. Инвестиционный кредит.

Конкретные ограничения суммы, срока и ставки брать из действующих настроек продуктов в БД или существующих конфигураций. Не создавать финансовые условия наугад.

## 1.4. Что входит в MVP

- регистрация и вход;
- подтверждение email;
- восстановление пароля;
- назначение банковских ролей через приглашения;
- администрирование сотрудников;
- первичная настройка компании;
- каталог кредитных продуктов;
- создание, сохранение и отправка заявки;
- список и карточка заявок;
- очередь банка;
- назначение ответственного;
- проверки и объяснимую оценку риска;
- запрос сведений;
- загрузка и проверка документов;
- банковское предложение либо отказ;
- принятие или отклонение предложения клиентом;
- история изменений;
- две темы;
- раскрывающееся меню;
- AI-помощник;
- новости/полезные материалы;
- основные настройки;
- корректные состояния загрузки, ошибок и пустых экранов;
- сквозные интеграционные тесты.

## 1.5. Что не нужно имитировать как реальный банк

Расчёт риска по правилам не является реальным финансовым андеррайтингом.

Не реализовывать и не обещать:
- реальную выдачу денег;
- открытие банковских счетов;
- проверку КИ через настоящее бюро без подключения;
- настоящий KYC/AML-процесс без соответствующих сервисов;
- юридически действительное подписание кредитного договора;
- фактическое одобрение кредита независимым AI.

Если в MVP отображается `COMPLETED`, это означает завершение оформления заявки, а не автоматическую реальную выдачу кредита.

# 2. ОБЩАЯ АРХИТЕКТУРА

## 2.1. Frontend

React + TypeScript + Vite + Mantine.

Frontend отвечает за:
- отображение;
- навигацию;
- состояние форм;
- запросы к API;
- оптимистичное/пессимистичное обновление UI;
- обработку загрузок, ошибок, подтверждений;
- доступность;
- темизацию.

Frontend **не отвечает** за:
- решение о доступности кредитного действия;
- присвоение ролей;
- расчёт авторитетного скоринга;
- окончательные переходы статусов;
- проверку принадлежности заявки;
- хранение секретов;
- подписание серверных решений.

## 2.2. Backend

FastAPI.

Backend отвечает за:
- аутентификацию;
- авторизацию;
- управление сессиями;
- работу с компаниями;
- валидацию;
- бизнес-состояния;
- транзакции;
- документы;
- скоринг;
- банковские действия;
- журнал событий;
- API для AI-помощника;
- договорённости об идемпотентности;
- генерацию OpenAPI.

## 2.3. PostgreSQL

Единое постоянное хранилище состояния продукта.

Не помещать авторитетные данные заявок или ролей в localStorage браузера.

## 2.4. Docker Compose

Рекомендуемые сервисы:
- frontend;
- backend;
- postgres;
- локальное хранилище документов или смонтированный защищённый volume;
- OPTIONAL: Mailpit для почты;
- OPTIONAL: средство просмотра БД для разработчика.

Конкретные имена и параметры брать из существующего Compose.

## 2.5. Принцип интеграции

Обязательная цепочка:

`FastAPI/Pydantic → OpenAPI → сгенерированные TypeScript-типы → типизированный API-клиент → React UI`

Если генерация типов уже существует, использовать текущий способ.

Избегать отдельного ручного поддержания двух несовместимых моделей одного и того же объекта.

# 3. ГЛОССАРИЙ И ДОМЕННАЯ МОДЕЛЬ

## 3.1. User

Человек с учётной записью.

У одного человека есть:
- уникальный внутренний ID;
- email;
- имя;
- системная роль или набор полномочий;
- состояние аккаунта.

Системная роль не должна доверяться данным браузера.

## 3.2. Organization

Юридическое лицо клиента.

Компания:
- имеет собственный идентификатор;
- содержит реквизиты;
- является владельцем заявок;
- может иметь пользователя-владельца и, при расширении, участников.

## 3.3. Organization Membership

Связь пользователя с компанией.

Рекомендуемая роль в компании для MVP: `OWNER`.

Потенциальные будущие роли: `EDITOR`, `VIEWER`.

Не смешивать роль `CLIENT` с полномочиями внутри компании.

## 3.4. Application

Кредитная заявка.

Содержит:
- идентификатор;
- человекочитаемый номер;
- компанию;
- продукт;
- запрошенные параметры;
- этап;
- создателя;
- ответственного сотрудника, если есть;
- версию или механизм конкурентного изменения;
- даты событий;
- ссылки на документы и решения.

## 3.5. Offer

Банковское предложение.

Отдельная сущность, в которой фиксируются **предложенные**, а не исходные параметры кредита.

## 3.6. Risk Assessment

Результат расчётной оценки риска с пояснениями.

Не равен банковскому решению.

## 3.7. Application Event

Запись истории действий по заявке.

Должна содержать действующего пользователя или системного актёра, действие, дату, связанный объект и данные, достаточные для объяснимой истории.

## 3.8. Document Request

Запрос банка на конкретные документы или сведения.

Отдельно от самого файла.

## 3.9. Auth Session

Серверная запись о действующей сессии пользователя.

## 3.10. Bank Assignment

Ответственный сотрудник по заявке.

Назначение должно проверяться сервером и учитываться при банковских действиях.

# 4. РОЛИ И РАЗРЕШЕНИЯ

## 4.1. CLIENT

Может:
- завершить регистрацию и настройку компании;
- просматривать профиль своей компании;
- редактировать разрешённые реквизиты;
- видеть разрешённые кредитные продукты;
- создавать черновики;
- редактировать свои черновики;
- отправлять заявки компании;
- просматривать заявки и историю своей компании;
- загружать документы;
- отвечать на запросы банка;
- видеть полученные предложения;
- принимать или отклонять предложения при наличии полномочия;
- использовать AI-помощника;
- менять пользовательские настройки.

Не может:
- назначать банковскую роль;
- просматривать заявки чужих компаний;
- видеть внутренние банковские комментарии;
- создавать банковские предложения;
- изменять риск-скоринг;
- самостоятельно устанавливать банковские статусы.

## 4.2. BANK_OFFICER

Может:
- просматривать разрешённую банковскую очередь;
- фильтровать и искать заявки;
- брать свободную заявку в работу;
- просматривать данные, проверки, документы и историю в рамках полномочий;
- выполнять действия по назначенной заявке;
- запрашивать сведения;
- создавать предложение;
- оформлять отказ с основанием.

Не может:
- приглашать других сотрудников;
- самостоятельно повышать роль;
- принимать оффер от имени клиента;
- менять заявки без проверки состояния;
- выполнять решения по чужой назначенной заявке без отдельного полномочия.

## 4.3. BANK_ADMIN

Может:
- видеть список сотрудников;
- приглашать новых сотрудников;
- отзывать приглашения;
- блокировать и восстанавливать доступ;
- переназначать заявки;
- просматривать журнал административных действий;
- управлять допусками в пределах политики системы.

**По умолчанию BANK_ADMIN не получает права принимать кредитные решения.**

Если текущая БД уже реализует более подробную матрицу полномочий, Codex должен сохранить совместимость и применить политику минимально необходимых прав.

## 4.4. Обязательные серверные проверки

Для любой защищённой операции:

1. Действительна ли сессия?
2. Активен ли аккаунт?
3. Имеет ли пользователь нужное полномочие?
4. Принадлежит ли объект разрешённой организации или банковской области?
5. Подходит ли текущий статус объекта?
6. Не изменился ли объект после загрузки формы?
7. Не является ли операция повтором уже выполненной команды?

Ни один из этих пунктов нельзя доверить только React Router или скрытой кнопке.

# 5. АВТОРИЗАЦИЯ, РЕГИСТРАЦИЯ И ВХОД

**Общий приоритет: P0.**

## AUTH-01. Регистрация клиента

**Триггер:** гость выбирает «Создать кабинет».

**Ввод:** имя, email, пароль и подтверждение пароля в интерфейсе.

**Backend обязан:**
- нормализовать email по принятой политике;
- проверить корректность полей;
- проверить пароль на действующую политику;
- не допускать массовое создание аккаунтов;
- создать пользователя с ролью CLIENT на сервере;
- сохранить пароль только как безопасный хеш;
- присвоить состояние ожидания подтверждения;
- сформировать одноразовый токен проверки email;
- отправить письмо либо доставить его через Mailpit в локальном MVP.

**Frontend обязан:**
- показать ошибки полей;
- не отправлять несколько регистраций по двойному клику;
- показать понятное сообщение о дальнейшем подтверждении;
- не создавать клиенту банковский доступ.

**Ошибки:** 400, 409/обобщённый ответ по политике, 422, 429, 500.

**Успех:** аккаунт создан; ещё не обязательно авторизован.

## AUTH-02. Подтверждение email

**Триггер:** переход по ссылке из письма.

Требования:
- токен одноразовый;
- ограничен по сроку;
- хранится безопасно, предпочтительно хешированным;
- подтверждает конкретную учётную запись;
- повторная попытка обрабатывается предсказуемо;
- неверный или истёкший токен не открывает кабинет;
- интерфейс предлагает повторное письмо, если это поддержано backend.

После подтверждения пользователь может войти и завершить настройку компании.

## AUTH-03. Вход

**Триггер:** email и пароль на `/login`.

Требования:
- единая страница для всех ролей;
- никаких переключателей «Я сотрудник банка»;
- backend определяет роль сам;
- неверные данные дают обобщённую ошибку без раскрытия наличия email;
- применяется защита от перебора;
- проверяются подтверждение email и состояние аккаунта;
- создаётся новая серверная сессия;
- после входа пользователь направляется по роли.

Маршрутизация после `/auth/me`:
- CLIENT без компании → `/client/onboarding`;
- CLIENT с завершённой настройкой → `/client/dashboard`;
- BANK_OFFICER → `/bank/applications`;
- BANK_ADMIN → `/bank/administration`.

Если пользователь открывал безопасную разрешённую страницу до окончания сессии, можно вернуть его на неё после повторного входа.

Не разрешать произвольные внешние redirect URL.

## AUTH-04. Текущий пользователь

Endpoint `/auth/me` — главный контракт начальной загрузки приложения.

Возвращает:
- идентификатор;
- email;
- имя;
- роль;
- состояние;
- разрешения;
- текущую организацию клиента, если есть;
- завершённость онбординга;
- информацию, необходимую для начального роутинга.

Не возвращает пароль, хеш пароля, секреты сессии или скрытые административные данные.

## AUTH-05. Выход

По нажатию «Выйти»:
- backend отзывает текущую сессию;
- браузер получает удаление cookie;
- frontend очищает приватные кеши запросов;
- пользователь попадает на `/login`;
- кнопка Back не должна позволять прочитать защищённые данные из активного состояния приложения без новой проверки.

## AUTH-06. Восстановление пароля

Сценарий:
1. Пользователь указывает email.
2. Интерфейс показывает обобщённое подтверждение отправки.
3. Backend создаёт одноразовый ограниченный токен.
4. Пользователь открывает ссылку.
5. Вводит новый пароль.
6. Backend обновляет хеш и отзывает соответствующие сессии.
7. Пользователь входит заново.

Не выдавать существование аккаунта по ответу формы восстановления.

## AUTH-07. Сессия истекла

При `401`:
- не повторять бесконечно защищённый запрос;
- очистить персональные данные из клиентского кеша;
- показать необходимость входа;
- не удалять уже сохранённый сервером черновик;
- после повторного входа заново загрузить данные с сервера.

Не хранить полный несохранённый финансовый черновик открытым текстом в localStorage без отдельного обоснованного решения по безопасности.

## AUTH-08. Управление сессиями

Для MVP:
- случайный криптографически стойкий идентификатор;
- серверная валидация;
- HttpOnly-cookie;
- Secure-cookie в HTTPS production;
- согласованная настройка SameSite;
- защита от CSRF для изменяющих операций;
- ограничение времени бездействия;
- абсолютный срок жизни;
- отзыв при блокировке пользователя;
- ротация при критическом изменении полномочий.

Предварительные параметры demo: 30 минут бездействия, 12 часов максимум. Codex должен вынести их в конфигурацию и проверить требования окружения.

Для production MFA банковских пользователей и дополнительная защита административных операций — обязательные вопросы отдельного security review.

# 6. ПРИГЛАШЕНИЯ И НАЗНАЧЕНИЕ БАНКОВСКИХ РОЛЕЙ

**Приоритет: P0.**

## ADMIN-01. Создание первого администратора

Создать защищённую CLI-команду или аналогичный процесс первоначальной настройки.

Требования:
- одноразовая инициализация;
- отсутствие пароля в исходном коде, миграциях и seed-файлах;
- отсутствие публичного endpoint «стать администратором»;
- логирование факта создания без секретов;
- защита от повторного случайного создания администратора.

## ADMIN-02. Просмотр сотрудников

Администратор открывает раздел «Сотрудники».

В таблице:
- имя;
- email;
- роль;
- состояние;
- дата приглашения/активации;
- последнее действие или вход, если хранится и доступен;
- действия по управлению.

Список должен иметь поиск и понятный пустой экран.

## ADMIN-03. Приглашение сотрудника

**Триггер:** «Пригласить».

**Ввод:** email и разрешённая роль.

Требования:
1. Проверить права администратора.
2. Проверить нормализацию email.
3. Проверить отсутствие несовместимой действующей учётной записи.
4. Создать приглашение с одноразовым токеном и сроком действия.
5. Отправить письмо.
6. Показать администратору статус приглашения.

Для MVP рекомендована политика: существующий CLIENT-аккаунт не превращается автоматически в BANK_OFFICER. При конфликте требуется отдельное явно спроектированное действие.

## ADMIN-04. Принятие приглашения

Сотрудник открывает ссылку.

Frontend:
- показывает, для какого email выписано приглашение;
- предлагает задать пароль;
- показывает срок действия и корректные ошибки.

Backend:
- проверяет токен;
- проверяет email;
- проверяет, что приглашение не отозвано и не использовано;
- создаёт либо активирует банковский аккаунт;
- связывает его с нужными разрешениями;
- помечает приглашение использованным;
- выполняет операцию транзакционно.

**Успех:** сотрудник может войти в банковский кабинет.

## ADMIN-05. Отзыв приглашения

Администратор может отозвать ещё не принятое приглашение.

После отзыва активация по старой ссылке должна быть невозможна.

## ADMIN-06. Блокировка сотрудника

Backend:
- меняет состояние доступа;
- отзывает активные сессии;
- запрещает дальнейшие банковские действия;
- записывает событие аудита.

Если за сотрудником закреплены заявки, показать администратору необходимость их переназначения. Не удалять историю прежнего ответственного.

## ADMIN-07. Восстановление доступа

Только через проверенное административное действие.

Восстановление не должно молча возвращать ранее отозванные сессии.

## ADMIN-08. Административный аудит

Фиксировать:
- кого пригласили;
- кто пригласил;
- когда приглашение принято/отозвано;
- кто заблокировал сотрудника;
- изменения назначений;
- существенные изменения прав.

Запись должна содержать время, актёра, действие и идентификатор объекта.

# 9. ЖИЗНЕННЫЙ ЦИКЛ КРЕДИТНОЙ ЗАЯВКИ

**Приоритет: P0.**

## 9.1. Согласованные статусы

- `DRAFT`
- `SUBMITTED`
- `VERIFYING`
- `UNDER_REVIEW`
- `NEEDS_INFO`
- `OFFERED`
- `ACCEPTED`
- `DECLINED`
- `REJECTED`
- `COMPLETED`

Не добавлять новые статусы без проверки существующей схемы и согласования переходов.

## 9.2. Матрица переходов

| Из | В | Инициатор | Условие |
|---|---|---|---|
| Нет заявки | DRAFT | CLIENT | Выбран доступный продукт |
| DRAFT | SUBMITTED | CLIENT | Полная валидация |
| SUBMITTED | VERIFYING | SYSTEM | Запуск проверок |
| VERIFYING | UNDER_REVIEW | SYSTEM | Проверки выполнены |
| VERIFYING | NEEDS_INFO | Допустимый банковский процесс | Есть корректный запрос сведений |
| UNDER_REVIEW | NEEDS_INFO | Назначенный BANK_OFFICER | Запрос дополнительных сведений |
| NEEDS_INFO | SUBMITTED | CLIENT | Отправлен ответ на запрос |
| UNDER_REVIEW | OFFERED | Назначенный BANK_OFFICER | Создан валидный оффер |
| UNDER_REVIEW | REJECTED | Назначенный BANK_OFFICER | Зафиксировано основание |
| OFFERED | ACCEPTED | Уполномоченный CLIENT | Принят текущий оффер |
| OFFERED | DECLINED | Уполномоченный CLIENT | Отклонён текущий оффер |
| ACCEPTED | COMPLETED | SYSTEM/уполномоченный процесс | Завершена предусмотренная финальная процедура |

Последний переход должен быть реализован только при наличии ясно определённого условия завершения в текущей бизнес-модели. Нельзя трактовать `ACCEPTED` как автоматическую фактическую выдачу кредита.

## 9.3. Общие правила переходов

- Сервер проверяет текущий статус.
- Сервер проверяет полномочия инициатора.
- Все связанные обновления и событие истории выполняются в одной транзакции.
- Недопустимый переход возвращает конфликт состояния.
- Повторный запрос не создаёт второе банковское решение.
- Важные команды используют идемпотентность.
- После успешной операции frontend перезапрашивает актуальные данные.

## 9.4. Пользовательские формулировки

| Код | Текст |
|---|---|
| DRAFT | Черновик |
| SUBMITTED | Отправлена |
| VERIFYING | На проверке |
| UNDER_REVIEW | На рассмотрении |
| NEEDS_INFO | Требуются сведения |
| OFFERED | Есть предложение |
| ACCEPTED | Предложение принято |
| DECLINED | Предложение отклонено |
| REJECTED | Отказано |
| COMPLETED | Завершена |

Содержание `NextActionPanel` должно зависеть не только от статуса, но и от фактических связанных данных.

# 10. КЛИЕНТСКИЙ СЦЕНАРИЙ: СОЗДАНИЕ ЗАЯВКИ

## APP-01. Создать черновик

**Ввод:** выбранный продукт.

**Проверки:**
- сессия CLIENT;
- компания определена;
- пользователь может действовать от имени компании;
- продукт доступен.

**Выход:** созданная заявка в DRAFT.

**UI:** переход к первому шагу мастера.

## APP-02. Заполнение мастера

Четыре шага:

1. Выбор продукта.
2. Сумма, срок, назначение финансирования.
3. Компания и финансовые сведения.
4. Проверка и отправка.

Примеры данных:
- productId;
- requestedAmount;
- termMonths;
- purpose;
- companySnapshot или ссылки на сведения компании;
- monthlyRevenue;
- monthlyExpenses;
- existingDebtPayments;
- связанные документы.

Реальные обязательные поля брать из существующей бизнес-модели.

## APP-03. Автосохранение

После ввода:
- показывать `dirty`;
- через небольшой debounce отправлять PATCH;
- показывать «Сохранение…»;
- по успешному ответу «Сохранено»;
- при неудаче «Не удалось сохранить» и повтор;
- не выдавать локальное изменение за успешное сохранение.

Проверить конфликт параллельных сохранений. Рекомендуется версионирование.

## APP-04. Продолжение черновика

Клиент может вернуться к DRAFT и продолжить с сохранённого этапа.

После обновления страницы поля загружаются из backend.

## APP-05. Валидация

Проверять:
- обязательность полей;
- допустимые суммы;
- допустимые сроки;
- правильные денежные значения;
- корректность финансовых показателей;
- отношения выбранного продукта и параметров;
- обязательные документы, если применимо.

Валидация frontend помогает пользователю, backend повторяет её полностью.

## APP-06. Отправка

При нажатии:
1. Проверить актуальность данных.
2. Заблокировать повторное нажатие.
3. Отправить команду `submit`.
4. Backend валидирует и переводит DRAFT → SUBMITTED.
5. Фиксируется событие истории.
6. UI получает актуальную заявку.
7. Пользователь открывает карточку заявки.

Отправленную заявку нельзя свободно редактировать как черновик.

## APP-07. Список заявок

Поддержать:
- список заявок своей компании;
- поиск по номеру/продукту при необходимости;
- фильтрацию по статусу;
- сортировку по обновлению;
- пагинацию;
- пустое состояние;
- переход в карточку.

## APP-08. Карточка заявки

Показывать:
- номер и продукт;
- статус;
- запрошенную сумму;
- срок;
- дату подачи;
- прогресс;
- `NextActionPanel`;
- историю;
- документы;
- предложение, если есть;
- контекстное открытие AI-помощника.

Главный приоритет — текущий статус и ближайшее действие, а не декоративная аналитика.

# 12. АВТОМАТИЧЕСКИЕ ПРОВЕРКИ И РИСК

## RISK-01. Запуск проверок

После SUBMITTED запускается предусмотренный серверный процесс.

Для MVP допустим синхронный или фоновый локальный расчёт, но статусы должны соответствовать фактическому завершению проверок.

Не показывать VERIFYING → UNDER_REVIEW, если расчёт упал, без предусмотренного сценария обработки ошибки.

## RISK-02. Детерминированная оценка риска

Использовать локальную понятную rule-based модель.

В расчёте могут участвовать:
- выручка;
- расходы;
- долговая нагрузка;
- запрошенная сумма;
- срок;
- другие поля действующего ТЗ.

Точные правила и пороги нужно сверить с существующим скорингом.

**Пример данных из изолированного теста:**
- ООО «Вектор»;
- выручка 1 800 000 ₽ в месяц;
- расходы 950 000 ₽;
- платежи по долгам 220 000 ₽;
- заявка №1042;
- сумма 3 200 000 ₽;
- срок 24 месяца;
- итог 67/100, MEDIUM — результат тестового примера.

Эти значения — тестовый seed, не обязательные финансовые нормативы.

## RISK-03. Объяснение результата

Показывать:
- значение;
- уровень;
- список факторов;
- короткое объяснение каждого;
- исходные числовые показатели;
- дату расчёта;
- версию правил расчёта, если предусмотрена.

Codex должен проверить фактическое направление шкалы: увеличивается ли риск с ростом балла или наоборот. Не менять семантику существующего скоринга молча.

## RISK-04. Ограничения

- Скоринг не равен кредитному решению.
- Клиент не получает доступ к служебным факторам без разрешения.
- Сотрудник видит источник данных.
- Результаты расчётов не изменяются произвольно на фронтенде.
- Повторный расчёт должен создавать новую версию или корректно обновлять связанную запись с сохранением истории по текущему доменному контракту.

# 13. ДОКУМЕНТЫ И ЗАПРОСЫ СВЕДЕНИЙ

## DOC-01. Список документов

Для клиента:
- название;
- тип;
- размер;
- дата;
- статус;
- принадлежность заявке;
- возможность просмотра/скачивания, если разрешено.

Для банка дополнительно:
- связь с запросом сведений;
- результат проверки;
- комментарии, если предусмотрены.

## DOC-02. Загрузка PDF

Валидация:
- допустимый формат;
- проверка типа содержимого на сервере;
- размер файла;
- ограничение доступа;
- безопасное имя;
- отсутствие прямой публичной выдачи из незащищённой папки.

Если прежнее ТЗ использует лимит 5 МБ, оставить его, если действующая конфигурация не устанавливает другое значение.

Хранить файл через существующий механизм хранения и метаданные в БД. Не предполагать, что файлы следует хранить прямо в таблице PostgreSQL.

## DOC-03. Запрос банка

Сотрудник выбирает «Запросить сведения».

Ввод:
- список запрошенных документов или требований;
- комментарий;
- при необходимости срок предоставления, если такой параметр реально поддерживается.

Backend:
- проверяет права и статус;
- создаёт запрос;
- переводит заявку в NEEDS_INFO;
- записывает историю;
- фиксирует связи между запросом и заявкой.

## DOC-04. Ответ клиента

Клиент:
1. Открывает запрос.
2. Читает требования.
3. Загружает документы.
4. Проверяет комплект.
5. Нажимает «Отправить ответ».

Backend:
- проверяет принадлежность заявки;
- валидирует комплект;
- фиксирует ответ;
- выполняет переход NEEDS_INFO → SUBMITTED;
- добавляет событие истории.

**Загрузка файла сама по себе не завершает запрос.**

## DOC-05. Просмотр и скачивание

Каждый запрос скачивания проверяет права на конкретную заявку и документ.

Не полагаться на секретность URL файла как на механизм защиты.

## DOC-06. Ошибки

Обработать:
- файл слишком большой;
- неподдерживаемый формат;
- временная ошибка хранения;
- документ уже загружен;
- запрос уже завершён;
- заявка перешла в другой статус;
- документ не принадлежит пользователю.

# 14. БАНКОВСКОЕ ПРЕДЛОЖЕНИЕ И ОТКАЗ

## OFFER-01. Создание предложения

Доступно назначенному сотруднику при допустимом статусе.

Поля:
- сумма предложения;
- срок;
- ставка, если применяется;
- комментарий;
- другие реальные условия существующего продукта.

Backend:
- проверяет роль и назначение;
- проверяет допустимость условий;
- сохраняет предложение отдельно от исходной заявки;
- переводит заявку в OFFERED;
- фиксирует событие истории.

## OFFER-02. Сравнение условий

Клиент видит таблицу:

| Параметр | Запрошено | Предложено |
|---|---|---|
| Сумма | Из заявки | Из оффера |
| Срок | Из заявки | Из оффера |
| Ставка | Только если запрашивалась | Из оффера |

Не придумывать запрошенную ставку, если пользователь её не вводил.

## OFFER-03. Принятие

Клиент открывает текущее предложение.

После явного подтверждения:
- backend проверяет доступ;
- проверяет, что оффер актуален;
- проверяет OFFERED;
- фиксирует принятие;
- переводит заявку в ACCEPTED;
- сохраняет событие.

После принятия больше нельзя повторно принять или отклонить тот же оффер.

## OFFER-04. Отклонение

Аналогично принятию:
- явное подтверждение;
- серверная проверка;
- переход OFFERED → DECLINED;
- сохранение события.

## OFFER-05. Отказ банка

Назначенный сотрудник может оформить отказ из разрешённого статуса.

Требования:
- обязательное внутреннее основание;
- отдельное разрешённое клиенту объяснение, если предусмотрено;
- подтверждение действия;
- переход UNDER_REVIEW → REJECTED;
- сохранение истории.

Не раскрывать клиенту закрытые служебные комментарии, если они не предназначены для него.

## OFFER-06. Завершение

После ACCEPTED отдельная предусмотренная бизнес-операция переводит заявку в COMPLETED.

Если в существующей модели такой операции нет, Codex должен выявить пробел и предложить минимальную явную реализацию, не маскируя её автоматической «выдачей кредита».

# 15. NEXT ACTION — ЕДИНЫЙ БЛОК СЛЕДУЮЩЕГО ДЕЙСТВИЯ

**Приоритет: P0.**

## ACT-01. Назначение

Компонент `NextActionPanel` объясняет человеку текущее состояние заявки.

Показывает:
- короткий заголовок;
- пояснение;
- текущий статус;
- основное действие при наличии;
- последнее событие, если есть.

## ACT-02. Правила

- DRAFT → «Продолжить оформление».
- SUBMITTED → «Заявка отправлена».
- VERIFYING → «Идут проверки».
- UNDER_REVIEW → «Банк рассматривает заявку».
- NEEDS_INFO → «Банк запросил сведения» + открыть запрос.
- OFFERED → «Подготовлено предложение» + сравнить условия.
- REJECTED → «Банк отказал» + доступная информация.
- ACCEPTED → «Предложение принято».
- DECLINED → «Предложение отклонено».
- COMPLETED → «Рассмотрение завершено».

Если фактические данные не позволяют предложить действие, кнопка не показывается.

## ACT-03. Источник данных

Статус и связанные объекты берутся из API.

Frontend может вычислять отображаемую подсказку через чистую функцию, но не должен менять серверное состояние.

## ACT-04. Переиспользование

Использовать на:
- главной клиента;
- странице заявки;
- в контекстной части AI-помощника при необходимости.

# 16. AI ASSISTANT 2.0 — ГИБРИДНАЯ ПАНЕЛЬ

Не принимает решения, не меняет статусы и не обещает одобрение.

## AI-02. Макет

Варианты:

## AI-04. Быстрые вопросы

На первом открытии показывать до трёх вопросов.

Примеры:

- документы → «Что нужно загрузить?»;
- оффер → «Почему предложенная сумма меньше?»;
- продукты → «Чем отличаются программы?».

После первого сообщения компактно сворачивать быстрые вопросы, оставляя возможность открыть снова.

## AI-05. Отправка

Frontend:
- добавляет вопрос в текущий диалог;
- отображает loading;
- отправляет текст и безопасный идентификатор контекста;
- получает ответ;
- показывает источники и действия;
- обрабатывает ошибку и повтор.

Backend:
- валидирует сессию;
- определяет организацию и права;
- загружает разрешённые данные самостоятельно;
- формирует ответ;
- возвращает только разрешённые источники;
- не позволяет клиенту получить чужую информацию через произвольный contextId.

## AI-06. Формат ответа

Логическая структура:
- messageId;
- text;
- source references;
- allowed actions;
- mode;
- createdAt.

`mode` может показывать `demo_rules` для локального FAQ-режима.

## AI-07. Источники

Источники должны ссылаться только на доступные пользователю данные:
- карточку заявки;
- историю;
- запрос банка;
- документы;
- оффер;
- описание продукта.

Не создавать ссылки на несуществующие ресурсы.

## AI-08. Контекстные действия

Примеры:
- «Открыть историю».
- «Открыть документы».
- «Сравнить условия».
- «Продолжить оформление».

Кнопки должны выполнять реальные переходы.

## AI-09. Хранение истории

История по возможности ключуется:
- текущим пользователем;
- контекстом;
- конкретной заявкой или продуктом.

Для MVP допустимо хранение истории в памяти клиентского приложения, если серверного хранилища нет.

Не выдавать временную историю за постоянную.

## AI-10. Состояния

Реализовать:
- первое открытие;
- пустой контекст;
- отправку;
- ожидание;
- ответ;
- ошибку;
- повтор;
- длинный ответ;
- смену заявки;
- смену темы;
- закрытие и повторное открытие.

## AI-11. Безопасность

- Отдельная проверка прав на каждый контекст.
- Никаких внутренних банковских полей клиенту.
- Не доверять инструкциям, найденным в загруженном PDF или тексте сообщения.
- Не исполнять действия по инициативе модели.
- Не отправлять персональные данные внешней LLM без отдельного решения по безопасности и конфигурации.

# 21. ЕДИНЫЕ API-КОНТРАКТЫ

## 21.1. Общие правила

Предлагаемый префикс: `/api/v1`.

Если префикс уже существует, сохранять его.

- JSON в UTF-8.
- Поля API в camelCase, если действующий контракт не определяет иное.
- На backend можно использовать snake_case с сериализационными alias.
- Внутренний идентификатор ресурса должен быть стабильным.
- Отображаемый номер заявки не использовать вместо внутреннего ID.
- Даты передавать в ISO 8601 с часовым поясом.
- Хранить время в UTC, показывать пользователю в его локальном часовом поясе.
- Денежные значения не передавать в двоичном `float`.
- Для денег рекомендуется целочисленное количество минимальных единиц или точная десятичная строка по фактической модели.
- Ставки не хранить в двоичном float.
- При возвращении коллекций использовать пагинацию.
- Не возвращать банковские внутренние поля клиенту.

Рекомендуется генерация TypeScript-клиента из OpenAPI FastAPI.

## 21.2. Общая форма ошибки

# 23. КОНКУРЕНТНЫЕ ИЗМЕНЕНИЯ И ИДЕМПОТЕНТНОСТЬ

**Приоритет: P0.**

## 23.1. Версия заявки

Рекомендуется использовать поле `version` либо эквивалентный существующий механизм.

При PATCH или критической команде frontend передаёт ожидаемую версию.

Backend:
- проверяет её;
- выполняет операцию при совпадении;
- увеличивает версию;
- возвращает актуальное состояние.

При конфликте возвращать `409`.

## 23.2. Идемпотентность

Критические операции:
- submit;
- information-response;
- создание банковского оффера;
- отказ;
- принятие оффера;
- отклонение оффера.

Должны быть защищены от повторного выполнения.

Допустимо применять `Idempotency-Key` с серверным хранением результата и привязкой к пользователю, операции и телу запроса.

Не использовать клиентский disabled как единственную защиту.

## 23.3. Атомарность

Изменение статуса и запись истории — одна транзакция.

Создание оффера и переход в OFFERED — одна транзакция.

Создание запроса документов и NEEDS_INFO — одна транзакция.

Назначение сотрудника должно предотвращать гонку двух одновременных claim.

## 23.4. Обновление UI

После успешной мутации:
- инвалидировать/обновить соответствующие query-кеши;
- перезагрузить заявку;
- перезагрузить историю;
- обновить NextAction;
- при необходимости обновить банковскую очередь.

После 409 обновить экран и объяснить пользователю конфликт.

# 25. СКВОЗНЫЕ ПОЛЬЗОВАТЕЛЬСКИЕ СЦЕНАРИИ

## SC-01. Новый предприниматель

Предусловие: пользователь не зарегистрирован.

1. Открывает регистрацию.
2. Вводит данные.
3. Получает сообщение о подтверждении.
4. Подтверждает email.
5. Входит.
6. Открывает онбординг.
7. Создаёт компанию.
8. Попадает на dashboard.
9. Видит доступные продукты и пустой список заявок.

Ожидаемый результат: CLIENT с активной компанией, без банковских прав.

## SC-02. Новый банковский сотрудник

Предусловие: есть BANK_ADMIN.

1. Администратор открывает управление сотрудниками.
2. Вводит email.
3. Создаёт приглашение.
4. Сотрудник открывает одноразовую ссылку.
5. Задаёт пароль.
6. Активирует аккаунт.
7. Выполняет вход.
8. Попадает в очередь банка.

Ожидаемый результат: только предусмотренные банковские полномочия.

## SC-03. Создание и отправка заявки

1. Клиент выбирает продукт.
2. Создаётся DRAFT.
3. Клиент вводит сумму и срок.
4. Заполняет данные компании.
5. Видит автосохранение.
6. Проверяет сводку.
7. Отправляет заявку.
8. Видит SUBMITTED.
9. Видит историю и следующий шаг.

Ожидаемый результат: заявка и событие зафиксированы в PostgreSQL.

## SC-04. Проверки и банковская очередь

1. Система запускает проверки.
2. Заявка получает VERIFYING.
3. Проверки завершаются.
4. Заявка переходит в UNDER_REVIEW.
5. Сотрудник видит её в очереди.
6. Сотрудник берёт в работу.

Ожидаемый результат: заявка имеет актуальный статус и ответственного.

## SC-05. Запрос документов

1. Сотрудник открывает назначенную заявку.
2. Выбирает запрос сведений.
3. Указывает необходимые документы.
4. Backend создаёт запрос и NEEDS_INFO.
5. Клиент видит предупреждение.
6. Загружает PDF.
7. Нажимает «Отправить ответ».
8. Backend переводит заявку в SUBMITTED.
9. Процесс повторных проверок запускается по предусмотренным правилам.

Ожидаемый результат: документы, история и статусы согласованы.

## SC-06. Банковское предложение

1. Заявка находится в UNDER_REVIEW.
2. Сотрудник вводит предложенные условия.
3. Backend создаёт оффер и OFFERED.
4. Клиент открывает сравнение.
5. Проверяет сумму, срок, ставку.
6. Принимает предложение.
7. Backend фиксирует ACCEPTED.

Ожидаемый результат: исходные условия сохранены, оффер отдельно зафиксирован, повторное принятие запрещено.

## SC-07. Отказ банка

1. Назначенный сотрудник открывает UNDER_REVIEW.
2. Выбирает отказ.
3. Вводит обязательное основание.
4. Подтверждает решение.
5. Backend фиксирует REJECTED и событие.
6. Клиент видит допустимое объяснение.

Ожидаемый результат: не раскрыты внутренние служебные данные.

## SC-08. AI-помощник по заявке

1. Клиент открывает заявку.
2. Открывает AI Drawer.
3. Видит правильный контекст.
4. Нажимает «Что со статусом?».
5. Backend проверяет доступ к заявке.
6. Возвращает ответ и разрешённый источник.
7. Клиент открывает историю через действие.

Ожидаемый результат: данные соответствуют именно этой заявке.

## SC-09. Смена заявки в AI

1. Клиент задаёт вопрос по заявке A.
2. Переходит на заявку B.
3. Контекст помощника обновляется.
4. Ответы не должны подставлять суммы A в заявку B.

Ожидаемый результат: контексты изолированы.

## SC-10. Сотрудник заблокирован

1. Администратор блокирует сотрудника.
2. Backend отзывает его сессии.
3. Его следующий банковский запрос не проходит.
4. Незавершённые заявки остаются в системе.
5. Администратор может переназначить ответственность.

Ожидаемый результат: доступ закрыт без потери истории.

## SC-11. Попытка открыть чужую заявку

1. CLIENT A меняет URL на ID заявки CLIENT B.
2. Backend проверяет принадлежность.
3. Не раскрывает данные.
4. Frontend показывает предусмотренную ошибку.

Ожидаемый результат: изоляция компаний подтверждена.

## SC-12. Конкурентный захват

1. Два сотрудника открывают неназначенную заявку.
2. Почти одновременно нажимают «Взять в работу».
3. Один получает успех.
4. Второй получает конфликт.
5. Второй видит актуального ответственного.

Ожидаемый результат: нет двойного назначения.

## SC-13. Истекшая сессия в форме

1. Клиент редактирует черновик.
2. Сессия истекает.
3. Сохранение получает 401.
4. UI не показывает ложное «Сохранено».
5. Клиент входит снова.
6. Система загружает последний действительно сохранённый черновик.
7. Если есть несохранённые данные в памяти приложения, интерфейс предупреждает о риске потери.

Ожидаемый результат: нет тихой потери или ложного сохранения.

## SC-14. Ошибка загрузки документа

1. Клиент выбирает неподходящий файл.
2. Получает понятное сообщение.
3. Выбирает корректный PDF.
4. Отправляет.
5. При ошибке сети загрузка не отмечается успешной.
6. Пользователь может повторить попытку.

## SC-15. Ошибка банковской операции

1. Сотрудник открывает устаревшую карточку.
2. В другой сессии статус меняется.
3. Сотрудник пытается создать оффер.
4. Backend возвращает 409.
5. UI объясняет, что заявка изменилась.
6. Данные обновляются.

Ожидаемый результат: недопустимое банковское решение не выполнено.

# 27. БЕЗОПАСНОСТЬ И ПРИВАТНОСТЬ

**Приоритет: P0 для базовых требований.**

## 27.1. Аутентификация

- Безопасное хеширование паролей.
- Уникальные сессии.
- Серверные таймауты.
- Rate limiting для входа, регистрации, восстановления.
- Проверка адреса электронной почты.
- Одноразовые токены.
- Защита от перечисления пользователей.
- Отзыв сессий при блокировке/смене полномочий.

## 27.2. Авторизация

- Default deny.
- Проверка роли.
- Проверка владельца/организации.
- Проверка назначения сотрудника.
- Проверка статуса операции.
- Защита от IDOR.

## 27.3. Cookies и CSRF

Если используется cookie-аутентификация:
- HttpOnly;
- Secure в HTTPS;
- подходящий SameSite;
- ограниченные область и срок действия;
- CSRF-защита для state-changing запросов;
- проверка Origin, где применимо.

Не хранить долгоживущие секреты аутентификации в localStorage.

## 27.4. Файлы

- Проверка доступа;
- проверка формата/сигнатуры;
- лимит размера;
- безопасные имена;
- не исполнять файл;
- не размещать приватные документы в общедоступной static-директории;
- учитывать необходимость антивирусной проверки при дальнейшем развитии.

## 27.5. API

- Валидация Pydantic;
- защита от mass assignment;
- ограниченный CORS;
- отсутствие stack trace в публичном ответе;
- correlation/request ID;
- запрет массовой выдачи чувствительных полей.

## 27.6. Аудит

Логировать:
- входы и значимые неудачи;
- блокировку и приглашения;
- изменения прав;
- банковские решения;
- изменения статусов;
- назначения;
- ответы на запросы банка.

Не логировать:
- пароль;
- session cookie;
- токены приглашений;
- тело приватных документов;
- неочищенные секретные данные.

## 27.7. AI

AI не должен:
- получать неразрешённые банковские данные;
- доверять пользовательским инструкциям для обхода прав;
- исполнять произвольные маршруты и команды;
- утверждать несуществующие финансовые факты.

## 27.8. Production limitation

Это хакатонный MVP. Для использования реальных банковских клиентов необходимы отдельные проверки:
- нормативного соответствия;
- KYC/AML;
- управления персональными данными;
- хранения и удаления документов;
- MFA;
- журналирования;
- отказоустойчивости;
- защищённости инфраструктуры;
- полномочий юридического представителя.

Отдельно отличать оформление кредитной заявки от денежного перечисления.

# 28. FRONTEND: ИНТЕГРАЦИЯ С API

## 28.1. Единый API-клиент

Использовать один типизированный HTTP-клиент.

Он должен:
- использовать общий base URL;
- передавать cookie с учётом конфигурации;
- передавать CSRF-токен;
- обрабатывать коды ошибок;
- поддерживать отмену устаревших запросов;
- не делать бесконечные повторные запросы после 401;
- передавать requestId для диагностики.

## 28.2. Источники данных

Не хранить отдельный «истинный» список заявок в React, независимый от сервера.

После мутаций данные синхронизируются с backend.

## 28.3. Router Guards

Использовать:
- проверку сессии;
- проверку роли;
- проверку завершённого онбординга;
- безопасное перенаправление.

Guards не заменяют backend security.

## 28.4. Формы

Использовать существующий подход проекта к формам. Не подключать новые библиотеки без пользы.

Особенности:
- локальная валидация;
- серверные ошибки;
- блокировка повторных команд;
- отображение автосохранения;
- обработка конфликта версии.

## 28.5. Кеш

Если проект использует TanStack Query либо эквивалент:
- системно ключевать запросы по пользователю/организации/ресурсу;
- очищать приватный кеш при выходе;
- обновлять связанные query после мутаций;
- не смешивать банковские и клиентские ответы в одной кеш-записи.

## 28.6. Типы

Генерировать TypeScript-типы из OpenAPI либо сохранять единый согласованный контракт.

Избегать повсеместного `any`.
